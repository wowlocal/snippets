# Промпты для агента: iPhone и iPad

Запускайте из корня репозитория. Подставьте версию; номер сборки берите из результата
загрузки или сохранённого `release.json`. iPhone и iPad используют одну сборку.

## Подготовить и отправить обновление на review

```text
Подготовь и отправь Snippets для iPhone/iPad версии <VERSION> на App Review.
Используй skills/release-snippets-ios/SKILL.md и docs/ios-release.md.

Это поручение включает подготовку и коммит относящихся к релизу изменений,
загрузку сборки в App Store Connect, обновление метаданных/скриншотов, публикацию
проверенной App Privacy декларации при необходимости, отправку на review и push
iOS-тега сборки в origin. После одобрения Apple оставь ручную публикацию.

Сначала проверь Git и фактическое состояние Apple. Сохрани чужую незавершённую
работу; не включай её в релиз без разрешения. При необходимости используй отдельный
worktree с согласованными коммитами. Определи предыдущую опубликованную iOS-версию.
Для старого релиза без достоверного тега не приписывай ему коммит по совпадению номера.
Подготовь честные release notes на русском и английском по проверенным изменениям,
проверь описания и изображения. Установи только iOS-версию и закоммить подготовку.

Проведи штатные проверки, используй testflight-ios.sh для загрузки. Не пропускай
тесты автоматически из-за отсутствующего симулятора. Проверь совпадение версии,
build, исходного коммита, Production CloudKit и сохранённых IPA/архива/dSYM.
Используй app-store-ios.sh prepare, validate, submit, status и push-tags.
Если нужная сборка уже загружена и имеет достоверный receipt, используй её повторно.

Исправляй обнаруженные readiness-блокеры через asc, где это возможно. Для вопросов,
которые доступны только в интерфейсе Apple, используй браузер и раздел «Браузерный
handoff» этого файла. Уже порученные действия выполняй без повторного согласования.
Если нужны вход, 2FA, неизвестные факты о продукте, новые юридические условия или
решение о включении чужой работы — запроси только недостающий ввод.

После сетевой ошибки сначала проверь серверное состояние. Не создавай дубликаты
версий/сабмишенов, не отменяй активное review и не заменяй опубликованные теги.
Заверши, когда Apple подтверждает WAITING_FOR_REVIEW либо уже IN_REVIEW для нужного
build. Если операция остаётся асинхронной, явно сообщи фактическое состояние и
оставшийся шаг. В отчёте укажи version/build, commit, тег и результат push,
место хранения артефактов, проверки и статус Apple. Не публикуй приложение в Store.
```

## Опубликовать одобренное обновление

```text
Опубликуй одобренный Snippets iPhone/iPad <VERSION>, build <BUILD>.
Используй skills/release-snippets-ios/SKILL.md и docs/ios-release.md.
Это поручение разрешает ручную публикацию именно этой сборки и push её iOS-тегов.

Проверь receipt, исходный коммит, тег сборки и build, выбранный в App Store Connect.
Не собирай новый бинарник. Если Apple ещё не одобрила эту сборку, сообщи её статус.
Если она ожидает developer release, выполни app-store-ios.sh release. Если CLI
не покрывает конкретный шаг, выполни его в браузере с проверкой version/build.
При необходимости входа/2FA попроси пользователя завершить вход.

Дождись подтверждаемого Apple состояния публикации в пределах текущей сессии,
затем выполни finalize и push-tags. Если обработка затянулась, сохрани receipt и
сообщи, что именно ещё ожидается, не называя релиз опубликованным. При сетевой
ошибке сначала проверь состояние, не нажимай Release повторно вслепую.
Проверь публичную страницу Store отдельно, если она уже обновилась. Не путай
принятый запрос публикации, статус Apple и распространение по storefront.
```

## Браузерный handoff: устранить конкретный блокер

```text
Продолжи текущий iOS-релиз Snippets <VERSION>, build <BUILD>.
Блокер: <EXACT_BLOCKER_FROM_READINESS_OR_APPLE>.
Предел уже разрешённого действия: <PREPARE / SUBMIT / PUBLISH>.
Прочитай docs/ios-release.md и сохранённый readiness.json, если он есть.

Сначала проверь asc <команда> --help: используй API/CLI для поддерживаемого шага.
Для App Privacy доступны scripts/app-store-privacy.sh plan/apply/publish при
авторизованной web-сессии. В браузер переходи, если CLI действительно не покрывает
шаг или не может использовать существующую сессию. Открой App Store Connect,
найди приложение по bundle ID com.khm.snippets и сверь команду, платформу iOS,
версию и build. Не выбирай приложение только по похожему имени.

Сними текущее состояние страницы и устрани именно указанный блокер:
— App Privacy: сопоставь ответы с Distribution/AppStore/privacy.json и текущими
  возможностями приложения; сохрани и опубликуй декларацию, если это входит в
  уже порученную отправку. Проверь, что публикация действительно завершилась.
— Поля страницы/review: используй утверждённые метаданные репозитория и известные
  приватные контактные данные; не выдумывай ответы, аккаунты или пароли.
— Отправка на review при недоступном API: проверь selected build и ручную публикацию,
  добавь версию к submission, проверь состав и отправь. Не включай посторонние items.
— Ручная публикация при недоступном API: только при разрешённом PUBLISH и одобрении
  указанной сборки выполни Release This Version, затем проверь результат.

Если нужен вход/2FA, дай пользователю завершить его в интерфейсе; не сохраняй
пароли, cookies и коды в репозитории или отчёте. Новые соглашения, налоговые/банковские
сведения и неизвестные compliance-факты передай пользователю с точным вопросом.
Поручение подготовить или отправить на review не разрешает публиковать приложение.

После изменения перечитай страницу, затем вернись к API-проверке, если она доступна.
Продолжи исходный workflow автоматически в его разрешённых пределах. Если действие
уже произошло, не повторяй его. Верни минимальное подтверждение состояния; скриншоты
с контактами, учётными данными или приватной информацией не включай в отчёт.
```

## Восстановить прерванный релиз

```text
Восстанови прерванный workflow Snippets iPhone/iPad <VERSION>, build <BUILD>.
Исходная задача: <SUBMIT / PUBLISH>. Последняя ошибка: <ERROR_OR_LOG_PATH>.
Используй docs/ios-release.md и skills/release-snippets-ios/SKILL.md.

Прочитай release.json и сверь IPA SHA-256, исходный коммит, iOS-теги и фактическое
состояние Apple. Сетевой сбой не означает, что операция не выполнилась.
После загрузки используй reconcile, после подготовки — повторяемый prepare,
после отправки — status и существующий matching draft. Не загружай тот же build
заново и не создавай новую submission, пока старая не проверена.
Не отменяй активное review и не передвигай теги без отдельного поручения.

После попытки публикации проверь releaseRequestedAt и состояние Apple. Если запрос
уже принят, продолжи ожидание/finalize. Если есть определённое подтверждение, что
запрос не принят, и версия остаётся PENDING_DEVELOPER_RELEASE, повтори точный запрос
публикации через asc или браузер в рамках исходного PUBLISH, затем finalize/push-tags.
При неопределённости сохрани артефакты и сообщи её, не выдавая догадку за успех.
```
