# P2: после recovery появляются копии уже подтверждённых собственных правок

**Статус: наблюдение на чистой синтетической библиотеке, требует локализации причин.** Мгновенное восстановление после kill прошло; проблема обнаружилась при последующем обмене с другими устройствами.

## Воспроизведение

1. Новый space и ровно три обычные записи. Все тестовые установки изолированы.
2. По очереди: macOS, iPhone, iPad, Android, Linux. Перед каждым изменением клиент успешно синхронизируется с последней серверной версией.
3. Клиент меняет содержимое `fields` и отправляет batch.
4. Gateway получает ответ backend с `outcomes.kind=accepted` (ровно 1), сохраняет только агрегат подтверждения и удерживает ответ клиенту.
5. Завершить настоящий процесс: SIGKILL Apple/Linux, `am force-stop` Android.
6. Перезапустить **ту же установку**, сохранив библиотеку и журнал. Проверить собственный текст, прежние ID и 3 записи.
7. Следующий клиент получает это изменение, делает своё и проходит тот же сценарий. После всей цепочки синхронизировать все пять клиентов ещё раз.

## Факт

Непосредственный recovery каждой платформы сохраняет свою принятую сервером правку и все 3 ID, без дополнительных записей. При последующем обмене:

- Mac, Android, Linux сначала имеют 3 записи;
- iPhone получает четвёртую запись — отключённую копию своего старого `audit-crash-iphone`;
- iPad получает четвёртую запись — отключённую копию своего старого `audit-crash-ipad`;
- основная запись у всех уже содержит более поздний `audit-crash-linux`.

После двух дополнительных кругов все пять клиентов сошлись на **5 записях вместо исходных 3**: лишние копии iPhone и iPad распространились на остальные устройства. Это не только промежуточное расхождение интерфейсов.

Эти правки были последовательными, и каждый следующий редактор предварительно получил предыдущую. Ожидается замена поля по подтверждённой линии изменений, без превращения старой подтверждённой версии в новый конфликт.

## Доказательства

- `/tmp/snippets-account-key-chaos/crash-clean/`: логи `1201`–`1216`, отдельное продолжение recovery Linux `1301`, финальная проверка `1302`–`1306`.
- Gateway marker проверяет **accepted**, а не только HTTP 200.
- `evidence/crash-recovery-result.json`: подтверждения пяти kill/recovery, итог и дополнительные круги обмена.
- Более простой одиночный kill/replay iPhone в `crash-minimal/` прошёл: 3 записи до, после, при повторе и на Mac. Он не закрывает проблему последовательного обмена после recovery нескольких клиентов.

Агрегат дополнительных кругов: сначала `[3,4,5,5,5]`, затем `[5,5,5,5,5]` и полное равенство снимков.

Один сбой продолжения возник из-за истёкшего вручную переданного access token (`authentication_required`); этот шаг не считать дефектом приложения. Продолжение запускалось после штатного refresh.

## Направление отладки

Проверить exact-offer echo, очистку pending journal после собственного принятого изменения, перенос confirmed base и timestamp/HLC между восстановлением и последующим входящим обновлением. Проверить, не становится ли подтверждённая правка снова локальной грязной версией из-за проекции в SnippetStore. Связь с потерей версии из P1 пока не доказана.

Не устранять симптом удалением копий или отключением preservation: это может скрыть потерю настоящих конфликтов. Добавить regression на последовательную цепочку: accepted-but-unacknowledged A → recovery A → B получает A и редактирует → A получает B.

## Установленная причина и исправление (ветка `fix/cloud-sync-conflicts`)

Журнал изменений сервера (space `8e21cc0e…`) показывает, что правки `audit-crash-iphone` и `audit-crash-ipad` **ни разу не были приняты сервером**. «Accepted» в стадиях crash iPhone/iPad (изменения 5–7 и 8–10) — побайтно идентичные повторы уже подтверждённых записей (те же ревизии, что 1, 4, 3). Диагностика симуляторов в эти стадии фиксирует `sync_triggered: key_changed`: `SyncCoordinator.discardAgreedBaseIfWireKeyChanged` выполнил reseal (`SyncJournal.stageConfirmedForTransportRekey`), который ставит подтверждённые байты предложением *впереди* более новой локальной правки. Ответ задержан, процесс убит; recovery разрешил reseal как точное эхо и сообщил Synced, оставив правку неотправленной (`uploaded 0`). Mac/Android/Linux затем правили старое значение, и позднейшая отправка iPhone/iPad стала настоящим конфликтом — копии были корректным сохранением, а не повторной проекцией подтверждённой правки.

Исправление: `SyncEngine.sync()` в производственной конфигурации (`SyncCoordinator`, `productionFollowUpRounds = 2`) выполняет ограниченные дополнительные раунды, пока раунд разрешает предложения и оставляет отправляемое намерение. Регрессия: `Tests/Core/SyncRecoveryFollowUpTests.swift` (reseal + потерянный ответ → recovery → B правит → A получает B: без копий). Почему отпечаток ключа в `UserDefaults` не сохранился между стадиями на симуляторе, не установлено; это отдельный вопрос стенда (сам reseal безопасен).
